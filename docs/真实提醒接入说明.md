## 先检查格式，再明确选择真实渠道

使用项目固定Node.js 22.22.2，在项目根目录执行：

```text
npm run notifications:verify
```

默认仅解析本机配置并检查格式，显示脱敏问题，写入 [提醒配置检查.json](提醒配置检查.json)。它不启动通知服务，不连接SMTP或飞书，不验证密码是否能认证，也不发送消息；`configured=true`仅代表本地格式校验通过。未指定`--live`的检查不会覆盖真实联调报告。

在用户明确批准渠道、测试目标及固定测试消息后，先构建，再选择其中一个渠道执行：

```text
npm run build
npm run notifications:verify -- --live --channel=email
npm run notifications:verify -- --live --channel=feishu
```

每条命令只选一个渠道，不接受自定义正文、任意收件人、业务项目或合同输入。现有目标已经完成本轮联调，应读取独立报告，不重复执行发送命令。固定正文为“这是一条投后管理系统渠道测试消息。”，飞书按配置添加关键字。邮件和飞书分别写入`docs/真实提醒联调-email.json`与`docs/真实提醒联调-feishu.json`。没有执行的渠道不创建通过记录。邮件当前已有3条尝试且已完成独立收件确认；普通verify按首次1attempt设计，恢复后的结论应读独立恢复及收件报告，不靠复跑或清台账验收。

CLI使用独立本机子服务、随机端口与隔离存储，不使用主数据库，不创建业务提醒或自动计划；模型保持mock、协议外发授权关闭、定时关闭，只让选定通知渠道使用live，未选渠道的凭据清空。仅填写真实凭据不会启用主服务自动发送。


本人发给本人时，USER、FROM和MAIL_TO在本机替换为已授权的本人地址。主服务保持mock，上述显式CLI仅在隔离子服务启用真实邮件。465使用隐式TLS并校验证书；改用非隐式TLS端口时，适配器仍要求STARTTLS与证书校验，不能通过关闭校验绕过连接问题。

当前项目没有SMTP代理配置功能。系统存在HTTP代理不表示SMTP会经代理发送；下述代理连接测试只是独立诊断，不能作为产品已支持代理的证明。

## 持久台账、锁和复跑

真实验证数据保存在本机生成目录：

```text
var/live-notifications/<channel>/<targetHash>/app.sqlite
var/live-notifications/<channel>/<targetHash>/verification.lock
```

`targetHash`根据规范化邮件目标或飞书Webhook生成；邮件顺序、大小写和重复项不会产生新的邮件测试身份。台账按渠道和目标摘要隔离，固定幂等键关联这条测试消息。锁以`wx`独占创建，防止两个进程同时开始验证；退出只清理自己拥有的锁，数据库和发送尝试保留用于核查。

只要已有任意批次，CLI就不再启动发送服务，包括queued、sending、unknown、retry_wait、failed、已成功或模拟完成状态；通常读取旧台账并更新脱敏报告，不追加真实尝试。第五项补修后，严格匹配固定合成内容、目标和零业务数据的过期sending会在锁内仅归并成unknown并立即停止，报告0新增及send_authorization_consumed=false；不做SMTP预检或自动继续重发。未过期租约、已成功及unknown历史不变。锁冲突、损坏或来源异常需先由维护人员核对，不删除台账、改收件人或改目标来绕过保护。这个隔离台账不属于主服务提醒中心，不应从主库页面查找该批次。

Ctrl+C或SIGTERM会停止自己创建的子服务并保存取消状态；发送已经请求时，取消不表示消息未送达。清理失败保留`cleanup_failed`，取消保留`cancelled`，迟到成功不能覆盖这些终态。报告不包含邮箱明文、应用专用密码或Webhook，只保留脱敏目标、摘要和稳定错误。

## 如何解释结果和核查unknown

| 状态 | 能证明的范围及下一步 |
|---|---|
| not_run | 没有执行真实发送；配置格式检查也使用此状态 |
| transport_accepted / receipt_pending | 传输服务接受了消息并留有成功尝试；实际收件仍须单独核对 |
| result_unknown / transport_state=unknown | 发送结果未知，可能已经被接收；保留台账，禁止自动重发 |
| failed_needs_review / existing_requires_review | 存在失败、退避或已有批次，停止新发送并人工核查 |
| cancelled / cleanup_failed | 本机执行被取消或清理失败，不能据此推断消息是否送达 |

unknown时先保留时间、批次与尝试记录，在发件端和获准收件端核对固定测试消息；检查收件箱、垃圾邮件及发件记录，记录独立收件证据。网络超时、当前搜索没有结果或取消，都不能证明未投递。确认送达后补充核查结论；确需再次发送时，须另有明确授权和原因，通过受审计的人工流程处理，普通`notifications:verify`不提供重发或重置开关；独立`notifications:resolve`只在下文明确授权与严格门槛下执行一次人工恢复。真实业务库中的unknown仍通过提醒中心填写核查原因、人工标记成功或确认重发，不与此隔离测试台账混用。
