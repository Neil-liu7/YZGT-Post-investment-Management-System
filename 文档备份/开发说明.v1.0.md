## 1. 产品目标与业务边界

系统用于管理投资完成后，增资协议、股东协议、补充协议、章程等交易文件约定的义务：保存文件和原文，辅助识别义务，确定起算条件与履行期限，形成可跟踪的事项，并通过邮件或飞书提醒相关人员。

目标流程：

```text
建立项目 → 上传并保存协议 → 解析原文 → AI 提取候选义务
    → 人工核对原文、义务和时间规则 → 确认生成事项
    → 跟踪履约、补充凭证 → 临期及逾期提醒 → 完成并留痕
```

首版重点是履约管理。投资估值、财务报表分析、基金核算、投资审批、电子签章等不纳入本次默认范围。AI 负责生成候选信息；正式生效的义务及时间规则必须经过人工确认。

### 2.3 重开发必须纠正的问题

| 问题 | 影响 | 新版本处理原则 |
|---|---|---|
| 所有期限均按实际出资日起算 | 签署后、某事件后、季度结束后的义务可能算错 | 每条义务有独立起算规则 |
| 工作日乘以 1.4，月份乘以 30 | 无法准确处理节假日、调休和自然月 | 保留原始数量、单位和日历规则 |
| 期限只有一个 `days` 字段 | 固定日期、循环、前置事件、持续承诺无法准确表达 | 采用结构化期限模型 |
| 只记录上传文件名 | 无法回看原文件、验证条款来源 | 保存原文件、文件版本和条款定位 |
| 导入时丢弃独立来源文件字段 | 同号条款跨文件混淆，错误去重 | 使用文档及条款标识关联 |
| 飞书档位判断从最大阈值开始取首个命中 | 剩余 7 天、1 天、当天均可能落入 30 天档，阻止后续推送 | 按当前阶段独立判断和记账 |
| 筛选后仅用可见卡片重建全部任务 | 拖拽会丢失筛选外事项 | 只更新顺序，不能替换或删除其他事项 |
| 新项目未初始化文件列表等集合 | 新建项目后立即上传可能报错 | 所有集合默认空数组，建立回归用例 |
| 整份 JSON 覆盖保存 | 并发操作可能互相覆盖，缺少审计和事务 | 按实体更新，使用版本校验与事务 |
| 保存请求未检查 HTTP 成功状态 | 接口保存失败仍可能被当作成功 | 前后端确认持久化结果，失败可见且保留待保存内容 |
| 服务运行在个人电脑 | 关机、休眠或服务停止后不能按时提醒 | 明确部署方式，支持漏扫恢复与运行状态检查 |

## 4. 用户操作流程

### 4.1 建立项目与关键事件

1. 新建项目，填写名称、公司和项目负责人。
2. 录入已知的协议签署日、我方出资日、交割日等事件；未知日期保持空，不用当天补齐。
3. 不同协议可以有不同签署日；分期出资和不同投资方的出资分别记录。
4. 项目可编辑或归档。删除采用软删除；存在关联文件、义务和通知记录时说明影响，不静默级联销毁。

### 4.2 上传、提取与审核

1. 上传文件并保存原始附件，展示上传与解析状态。
2. 解析文本，记录页码、段落或文字区间等能够可靠获得的定位信息。
3. 发起提取任务；候选义务关联具体文件版本、原文片段和模型处理记录。
4. 审核页面逐条展示原文与提取结果，可修改、勾选导入、忽略或标记待确认。
5. 对标题、说明、义务主体、负责人、条款号、时间类型、起算条件、期限单位和重复周期进行确认。
6. 只将已选且通过校验的候选转为正式义务；重复确认同一候选不得重复创建。
7. 无法确定起算条件或日期的事项进入“待确定期限”，不生成伪造截止日，不参加逾期判断。

### 4.3 执行与完成

1. 负责人将事项从待开始改为进行中，记录进展或备注。
2. 已完成事项记录完成日期、操作人及可选凭证；特定义务是否强制凭证由业务规则决定。
3. 如需复核，可在 P1 增加“提交完成、审核通过、退回”流程；首版不把手工改状态等同于经过审核。
4. 重新打开已完成事项必须记录原因；保留原完成记录，重新评估未来提醒。
5. 修改截止规则、手动覆盖截止日或取消事项时，记录修改前后值及原因。

## 5. 功能要求

### 5.1 项目和文件

- 项目基础字段：项目名、公司全称、负责人、备注、归档状态及创建更新时间。
- 原文件支持预览或受控下载；同名文件不得覆盖已有原件，使用内容摘要和版本号区分。
- P0 支持文字型 PDF、DOCX、TXT、Markdown，单文件 20MB 为建议初始上限，可配置；前后端保持一致。
- 旧版 `.doc` 给出转换为 DOCX/PDF 的提示。扫描件或加密、损坏文件分别给出可理解的错误；OCR 属 P1。
- 文件移除不得顺带删除已确认义务；有引用时可归档或拒绝删除，并提示关联事项。
- 记录解析器、提取模型、提示词版本、处理时间和失败原因；重新提取生成新批次，不覆盖人工修改。
- 协议文本和附件不直接暴露在公共静态目录中。是否允许发送给外部模型需在部署配置中明确。

### 5.2 AI 候选义务

- 模型输出采用受校验的结构，不能仅依赖提示词保证正确。
- 候选信息包括原文、来源定位、义务主体、动作、交付物、触发条件、期限规则及未确定项。
- 一条原文可以对应多个动作和不同截止要求，允许拆分；分拆后仍关联同一原文。
- 区分到期交付、周期报送、持续性承诺、条件触发义务及权利行使窗口，避免全部转成普通截止任务。
- 内容裁剪、分段时保留条款上下文。规则预筛不能成为固定日期或周期表述进入模型的唯一门槛。
- 缺少期限或条件时返回待确认，禁止补成 30 天、365 天等默认业务期限。
- 重试应有超时、次数和退避上限；失败批次可以重试，已确认事项不重复导入。
- 去重优先依据文档版本、候选标识、原文位置和义务内容；相同标题或相同条款号不能单独作为去重键。

### 5.3 事项与看板

- 事项字段包含标题、说明、义务主体、负责人、来源、执行状态、截止状态、截止日、完成信息、备注和排序。
- 执行状态使用 `pending`、`doing`、`done`、`cancelled`；逾期是根据日期计算的展示状态，不覆盖执行状态。
- 截止状态独立记录为已计算、待事件、待确认或人工指定，不能用 9999 等哨兵天数代替。
- 看板展示项目完成率、待开始、进行中、已完成、临期、逾期及待确定期限数量。
- 建议完成率口径为：已完成执行事项数 ÷ 未取消、未删除的执行事项总数；候选和未来尚未生成的周期不计入。
- “即将到期”默认指未完成且剩余 0 至 7 天；已逾期指未完成且截止日在今天之前。
- 支持状态筛选、负责人筛选和按截止日排序；拖拽只更新手动排序字段。
- 对筛选后的子集调整顺序，不能改动其他事项的存在性、业务字段及相对次序。
- 服务端持久化数据是权威来源，浏览器只作缓存或保留未提交草稿。保存失败显示“未保存”和重试入口，不能显示成功；空数据库展示空状态，存储损坏则保护原数据并报告故障，不自动填入示例数据。

## 6. 期限计算模型

### 6.1 基础约定

业务日期以 `YYYY-MM-DD` 保存，提醒时区默认 `Asia/Shanghai`。发送、修改等时间点另以带时区的时间戳记录。禁止使用运行电脑的本地时区隐式决定业务日期。

保留合同原始期限数量和单位。自然日、工作日、自然月、自然年必须分别计算；不使用工作日乘以 1.4、月乘以 30 或年乘以 365 作为正式期限算法。

起算日是否计入、届满日是否顺延、自然月末如何处理均属于明确的规则字段。建议技术初始值为“不计起算日、非工作日不自动顺延、月末采用目标月最后一天”，但仅在审核者确认对应规则后生效；有歧义的条款保留待确认状态。这里的默认值不表示统一法律口径。

### 6.2 支持的规则类型

| 类型 | 业务例子 | 实现要求 |
|---|---|---|
| 固定日期 | 2029 年 12 月 31 日前完成实缴 | 保存具体日期，不能转成距出资日的估算天数 |
| 相对日期 | 本协议签署后 3 个月内 | 指向该协议签署事件，保存 3 和自然月单位 |
| 工作日期限 | 收到款项后 5 个工作日内 | 指向收款事件，使用指定工作日日历 |
| 事件依赖 | 工商变更完成后 5 个工作日交付材料 | 前置事件未登记时保持待事件，发生后计算 |
| 复合偏移 | 交割后第 30 日起算 5 个工作日内 | 分别保存 30 自然日和 5 工作日步骤，不丢弃前半段 |
| 多条件比较 | 两个日期以孰早或孰晚为准 | 明确 `earliest` / `latest` 以及全部参与条件 |
| 周期义务 | 每季度结束后 30 日内报送 | 按每个季度生成独立执行事项，分别完成及提醒 |
| 持续性义务 | 持股期间不得迁址 | 保存有效区间及检查计划，不仅在区间末尾生成一条交付任务 |

复合条件缺少必要事件时，不把未知值当作今天，也不把缺少的偏移视为零。必要分支齐全后计算；确需提前给出确定期限时，必须通过人工指定并记录依据。

### 6.3 工作日日历与周期

- 工作日日历记录地区、日期、工作或休息标记、版本和来源；既支持法定假期，也支持调休工作日。
- 未配置完整日历时，可以提供“仅排除周末”的预估，但必须标为待确认，不能冒充已核准期限。
- 更新日历或关键事件后列出受影响事项，由确认操作生成新版本；保留旧计算结果与原因。
- 人工指定的截止日保存操作者、原因及覆盖状态。自动重算先给出差异，不能静默覆盖人工指定值。
- 周期规则保存频率、周期起止、报送偏移、启用和终止时间；首个周期必须人工确认，不能根据出资日随意推断。
- 建议预生成未来 12 个月的执行事项，之后按计划补充；使用“义务＋周期标识”唯一约束防止重复生成。
- 持续性义务分别显示履行期间、检查时间和异常记录；到达区间末日不能自动判定历史期间全部合规。

## 7. 提醒与发送规则

### 7.1 渠道与范围

| 渠道 | 建议默认规则 | 内容与行为 |
|---|---|---|
| 自动邮件 | 每周一 09:00，上海时区 | 所有未归档项目中，未完成且逾期或 7 天内到期的事项 |
| 手动邮件 | 用户预览后点击发送 | 默认汇总所选范围的全部事项及状态，包括已完成项；允许编辑收件人、主题和正文 |
| 飞书群卡片 | 每天 09:30 扫描，提前量默认 30 天 | 按项目分卡片，列出协议、条款、事项、截止日、剩余天数及负责人 |

自动邮件无临期事项时，建议延续旧版发送“本周无临期事项”说明，并允许配置为跳过。邮件收件人和飞书群默认由部署方配置，禁止继承代码中写死的个人邮箱。

待事件、待确认的事项不作为逾期事项推送，可在单独的“待补充信息”汇总中展示。取消、已完成、归档事项不再新建履约催办通知；已排队但未发送的通知在发送前重新校验。

### 7.2 飞书档位与补扫

建议提前量取 1 至 90 天。档位集合为去重后的 `[提前量, 7, 1, 0]`，只保留不大于提前量的非负档位。例如提前量为 3 天时，使用 3、1、0 档，不再在 7 天时发送。

默认提前量 30 天时，当前阶段判断如下：

| 剩余自然日 | 当前阶段 |
|---|---|
| 大于 30 | 不提醒 |
| 8 至 30 | T-30 |
| 2 至 7 | T-7 |
| 1 | T-1 |
| 0 | 当日 |
| 小于 0 | 逾期阶段，与当日分开记录 |

- 每个事项、每个有效时间版本、每个渠道的每个阶段只产生一个自动通知事件。
- 服务恢复后若跨过多个阶段，建议只补当前最紧迫阶段，不连发已过时的全部档位。
- 逾期默认首次发现时提醒一次；是否每天、每周重复催办为待确认配置，不能无限重复发送。
- 修改标题或负责人不重置已发送档位。确认调整截止日或提醒策略后建立新的提醒计划版本，并在变更确认页展示会产生的提醒。
- 分组卡片的标题与明细必须属于同一项目，不能混用其他项目数据。

### 7.3 可靠发送与审计

- 到期扫描先在事务中生成唯一通知事件，再进入发送队列，不能由扫描过程直接无限并发调用外部服务。
- 同时运行两个扫描任务时，通过唯一键和任务锁保证只创建一份通知事件。
- 记录待发送、发送中、成功、明确失败、结果未知、跳过等状态，以及尝试次数和服务端返回标识。
- 明确失败可以按退避策略重试；建议上限 3 次。超时但无法确认对方是否已接收时，标记“结果未知”，不能当作确定失败无限重发。
- SMTP 和机器人接口未提供可用的端到端幂等能力时，不承诺绝对只送达一次；需要保留结果未知的人工处理入口。
- 发送前校验最新任务状态和计划版本，防止完成、取消或改期之后仍发出旧通知。
- 手动发送和测试消息也记录操作人、时间、对象和结果，但不消耗自动提醒档位。
- 提供只预览不发送的模式。开发和自动化测试必须使用模拟发送器，不接入真实收件人或群机器人。
- 保存每次扫描的开始、完成、失败和恢复情况；能看出上一次扫描是否成功。

## 8. 数据结构建议

采用关系型数据模型，使用稳定标识和外键，不再整包覆盖全部业务数据。下表是逻辑实体，不强制对应同名数据库表。

| 实体 | 关键字段与用途 |
|---|---|
| Project 项目 | `id`、名称、公司、负责人、归档状态、`version`、创建更新时间 |
| Document 协议文件 | `id`、项目、原文件名、格式、大小、摘要、存储位置、文件版本、解析状态 |
| Clause 原文条款 | `id`、文档版本、条款号、原文、页码/段落/文字区间；无法定位的字段留空 |
| ExtractionRun 提取批次 | 文档版本、模型与提示词版本、状态、错误、处理时间 |
| DraftObligation 候选 | 批次、原文关联、提取结果、未确定项、审核状态、确认后的义务标识 |
| Obligation 履约义务 | 项目、文档及原文、义务类型、主体、交付物、原始期限表达、时间规则、负责人、审核状态 |
| ProjectEvent 关键事件 | 项目、协议或投资方范围、事件类型、发生日期、登记人、证明材料和版本 |
| Task 执行事项 | 义务、周期标识、标题、负责人、执行状态、截止状态与日期、规则快照、排序、版本 |
| TaskEvidence 履约记录 | 事项、备注、附件、完成时间、操作人、重新打开或取消原因 |
| ReminderPolicy 提醒策略 | 渠道、范围、扫描计划、时区、提前量、逾期频率、启停及版本 |
| NotificationEvent 通知事件 | 渠道、规范化接收目标、项目/事项范围、计划版本、阶段或周报周期、唯一业务键、内容快照、状态 |
| NotificationAttempt 发送尝试 | 通知事件、尝试序号、开始结束时间、结果、外部返回标识、脱敏错误 |
| AuditLog 操作日志 | 实体与标识、操作类型、操作者、时间、修改前后值、原因 |
| WorkCalendar 工作日日历 | 地区、版本、每日日历标记、来源、确认状态 |

核心关联：一个项目有多个文档和关键事件；一个文档有多个条款与提取批次；一个义务可引用多个条款、生成多个周期事项；一个通知事件可以关联多个事项，一个事项也可以进入多个通知事件。通知与事项关联需保存发送时的截止日及阶段快照。

关键约束：

- 同一候选只能确认生成一次正式义务；同一义务同一周期只能生成一个有效执行事项。
- 相同内容文件可以提示重复，不能把不同项目或不同版本的文件关系自动合并。
- 通知事件设置与业务粒度一致的唯一键：单事项提醒包含事项、渠道、规范化接收目标、时间计划版本和阶段；项目卡片或周报包含项目/范围、渠道、接收目标和发送周期，并通过关联记录追踪事项。渠道不同或收件目标不同，分别记账。
- 业务修改带版本号，冲突返回明确错误，避免最后一次保存静默覆盖前一次修改。
- 归档、软删除、恢复及审计日志在同一事务中完成；单条任务更新不接受客户端上传全库替换。

## 9. 接口规划

建议统一前缀 `/api/v1`。以下为接口契约草案，前后端开发前应补成机器可校验的接口定义；不得直接复用旧版整包数据写接口作为新系统的主要保存方式。

| 方法与路径 | 用途 |
|---|---|
| `GET /health` | 最小服务健康状态，不包含凭据及项目内容 |
| `GET /projects`、`POST /projects` | 查询、新建项目 |
| `GET /projects/{id}`、`PATCH /projects/{id}` | 读取、按版本修改项目 |
| `POST /projects/{id}/archive` | 归档或恢复项目，记录操作 |
| `POST /projects/{id}/documents` | 上传文件，使用 multipart，返回文档标识及处理状态 |
| `GET /documents/{id}`、`GET /documents/{id}/content` | 文件元信息和受控预览/下载 |
| `POST /documents/{id}/extractions` | 创建提取任务，异步返回任务标识 |
| `GET /extractions/{id}` | 查询进度、候选结果和失败原因 |
| `PATCH /draft-obligations/{id}` | 修改候选义务及审核状态 |
| `POST /extractions/{id}/confirm` | 按候选标识选择导入，返回已创建、跳过和失败明细 |
| `GET /projects/{id}/obligations`、`POST /projects/{id}/obligations` | 查询或手工创建义务 |
| `PATCH /obligations/{id}` | 修改义务；涉及期限时返回影响范围 |
| `POST /deadline-rules/preview` | 只计算并解释规则，不修改业务、不发送消息 |
| `GET /projects/{id}/events`、`POST /projects/{id}/events` | 查询或登记关键事件 |
| `PATCH /events/{id}` | 修正事件，返回受影响事项，经过确认后重算 |
| `GET /tasks`、`PATCH /tasks/{id}` | 筛选查询、按版本修改事项 |
| `PATCH /projects/{id}/task-order` | 仅提交局部排序信息，不删除其他事项 |
| `POST /tasks/{id}/complete`、`POST /tasks/{id}/reopen` | 完成、重新打开事项，附原因或凭证 |
| `POST /tasks/{id}/cancel` | 取消事项并停止未发送通知 |
| `GET /dashboard` | 按统一口径查询看板统计 |
| `GET /settings`、`PATCH /settings` | 查询、修改允许公开的设置；敏感配置仅返回已配置状态 |
| `POST /reminders/preview` | 按范围生成邮件/卡片预览，不触发真实发送 |
| `POST /reminders/send` | 发送用户确认的手动消息，带幂等请求标识 |
| `POST /notifications/test` | 明确触发测试消息，单独记账 |
| `GET /notification-events` | 查询发送记录、失败和结果未知事项 |
| `GET /audit-logs` | 查询业务变更历史 |
| `POST /imports/legacy/preview`、`POST /imports/legacy/confirm` | 旧版数据迁移预览与确认 |

接口要求：

- 异步任务创建返回 202 和任务标识；上传失败、解析失败、模型失败分别展示，支持重试。
- 写请求校验文件归属、关联实体、字段类型、规则完整性与版本；批量写入明确事务边界和部分失败语义。
- 版本冲突使用 409，超限使用 413；其他校验错误使用稳定错误码和可理解说明。
- 查询支持分页和受限的排序字段。返回统一的 `data`、`error`、`request_id`，不得回显密钥、原始服务堆栈或数据库连接信息。
- 发送端从服务端读取受控范围的数据，不接受客户端任意替换全部项目后作为自动周报依据。
- 对创建、确认导入、手动发送等操作支持幂等请求键；幂等键与参数摘要绑定，避免同键不同内容被误认为同一次请求。

## 10. 技术组织与跨平台运行

### 10.1 架构建议

建议沿用浏览器界面加 Node.js 服务的形态，将业务逻辑从大 HTML 文件中拆出。具体前端框架及数据库产品仍待确认，不依赖某个框架才能表达上述业务规则。

```text
浏览器界面
  └─ API 层：输入校验、身份与权限、版本冲突处理
      ├─ 项目 / 文件 / 原文 / 候选审核
      ├─ 义务 / 事件 / 期限引擎 / 执行事项
      ├─ 扫描 / 通知队列 / 邮件与飞书适配器
      └─ 数据访问 / 审计 / 备份
```

- 单机单实例可以采用嵌入式关系型数据库；若有多人并发、多个服务实例或共享部署，应据实际负载选用服务型关系数据库。
- 原始文件使用独立存储目录或对象存储；数据库保存文件元信息，备份包含文件与数据库的对应快照。
- 期限引擎不依赖页面、邮件或模型接口，应能独立验证。模型、邮件和飞书通过可替换适配器接入。
- 依赖版本、运行时版本和迁移版本在项目中固定，并记录可复现安装方式；开发启动时选择受维护的运行时版本。

建议目录：

```text
apps/web/             界面及交互
apps/server/          API 和后台任务入口
packages/domain/      业务实体、期限规则、状态与统计口径
packages/integrations/ 模型、解析器、邮件、飞书
database/             数据结构与迁移
storage/              本地附件，排除版本管理
tests/                关键规则、接口和完整业务流程验证
docs/                 开发、部署和运维文档
```

这是一种模块划分建议，不要求首版拆成多个独立部署的服务。

### 10.2 Windows 和 Mac

- Windows、Mac 提供等价的安装、启动、停止说明；路径使用系统路径接口，覆盖中文目录及带空格目录。
- 新版提供 Windows 和 Mac 启动入口，检查运行环境和依赖，等待健康检查通过后再打开浏览器。
- 端口占用时提示现有服务或给出可选择端口，不使用无差别强制结束其他进程的做法。
- 本地单人模式默认仅监听本机；局域网或服务器模式必须显式配置访问方式和权限。
- 需要全天自动提醒时部署为持续运行的服务，具备自动重启、日志轮换、备份和扫描状态检查。
- 关机、休眠期间不承诺按时发送；恢复后按照第 7 节的补扫策略处理，不伪造已经发送记录。
- 两台电脑分别安装时，数据库及附件默认各自独立；如需共享同一份数据，应连接同一受控服务，不把“跨平台可运行”当作“自动同步”。

## 11. 配置与数据保护

- 配置按开发、测试、生产区分。仓库只放无真实凭据的示例配置，不能复制旧版 `.env` 的值进代码或文档。
- 敏感配置包括模型密钥、SMTP 密码、飞书 Webhook；仅服务端使用。界面只显示配置状态，日志脱敏。
- 静态托管仅公开前端构建产物；数据库、附件、源代码、日志和备份均不放入静态目录。
- 文档文本、文件名、项目名和模型输出均按不可信内容处理；网页与 HTML 邮件进行必要转义。
- 上传同时校验扩展名、文件类型、大小和解析结果，生成服务端存储名，禁止客户端文件名控制磁盘路径。
- SMTP 默认验证 TLS 证书；确需例外时使用显式配置和原因，不沿用旧版全局关闭验证。
- 正式数据变更前保留可恢复备份；通过一次独立恢复验证确认数据库和附件均可恢复。
- 共享部署增加身份认证、项目范围权限、HTTPS、请求限流及受控文件下载；在这些条件满足前不开放公共访问。

## 12. 旧版数据迁移

### 12.1 迁移原则

旧版 `data.json` 作为导入源，先只读备份，保留文件摘要与导入批次。迁移采用“预览 → 人工确认 → 执行 → 对账”，不得覆盖原文件，也不直接沿用旧系统的外部服务凭据和收件人。

迁移与开发期间关闭真实自动发送，完成业务审核后单独启用提醒。

### 12.2 字段处理

| 旧字段 | 新版处理 |
|---|---|
| `projects[].id/name/company` | 建立项目并保留旧标识映射 |
| `agreementSignDate` | 导入为待核对的签署事件；多协议情况下不能自动认定均在同一天签署 |
| `actualInvestDate` / `investmentDate` | 导入出资事件，保留来源；旧字段只用于兼容 |
| `uploadedFiles` | 建立“原文件待补传”记录，不能显示为原文件已经归档 |
| `agreements[].clauses` | 作为旧条款文本导入，标注来源待核对，不能假定等于已上传文件的真实内容 |
| `tasks[].title/desc/clause/owner/status` | 保留内容和状态；负责人名称可以暂存，后续映射用户 |
| `tasks[].days` | 记录在迁移原始字段中；如需展示旧版计算日，标明“历史估算”，等待重新核定规则 |
| `settings` | 只迁移经过确认的非敏感设置；邮箱与通知计划先预览确认 |
| 飞书已推送状态文件 | 存在时保留历史记录，不直接当作新计划已完成，也不默认为全部重发 |

不能从旧版 7 天倒推出原文一定是 5 个工作日，也不能从 365 天推断原文一定是 1 年。不能把所有事项都自动确认成“出资后 N 个自然日”。

已完成事项继续保持已完成状态，但旧数据没有记录的完成时间、凭证和审核人均留空，不能补造。来源只有条款号时标记“来源待核实”，不能自动归到文件列表的第一份协议。

### 12.3 对账与回滚

- 对比项目数、事项数、状态分布、旧新标识映射及待核对来源数量。
- 同一源文件重复导入能够识别同一批次，支持安全重试，不重复创建项目或任务。
- 对无法自动映射的来源、日期、负责人和条款生成异常清单。
- 回滚只撤销该导入批次产生且未被后续业务修改的数据；已被编辑的数据停止自动回滚并提示处理范围。
- 通过抽样原文核对和数据总数对账后再开启提醒，避免历史错误期限形成批量误报。

## 13. 建议开发顺序

| 阶段 | 主要工作 | 阶段交付与退出条件 |
|---|---|---|
| 0 需求确认 | 确定部署场景、义务类型、日期口径、权限和提醒策略 | 决策记录、验收样例、业务原型 |
| 1 基础底座 | 数据结构、项目、文件存储、事件、日志、配置、基础运行入口 | 新项目在 Windows/Mac 均可创建并立即上传文件；备份可恢复 |
| 2 期限与事项 | 规则引擎、手工义务、周期生成、事项状态、筛选排序和看板 | 先用人工录入走通完整流程，日期核心用例通过 |
| 3 文档与 AI | 文本解析、提取批次、原文定位、逐条审核和幂等导入 | 同一文件可安全重提取，人工修改不丢失 |
| 4 提醒中心 | 预览、邮件/飞书适配器、计划、队列、日志、补扫和重试 | 模拟渠道完成全部提醒场景，外部联调由明确操作触发 |
| 5 迁移与发布 | 迁移预览、对账、回归、启动说明、运行维护 | 旧数据核对完成，恢复演练与跨平台验收通过 |

不预设交付天数；阶段工期取决于部署方式、团队人数、OCR 和协作是否纳入首版。

## 14. 验收标准

验收中的起算和顺延口径使用明确测试规则，不代表对所有协议采用相同解释。自动化验证使用隔离数据库、合成文件与模拟发送器。

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A01 | 新建项目后不刷新页面，立即上传首个文件 | 上传成功，空文件列表等默认字段完整 |
| A02 | 同名但内容不同的两个协议文件 | 原件均保留，版本和来源可区分 |
| A03 | 上传扫描件、损坏件、加密件或超限文件 | 明确显示对应错误，不生成成功假记录 |
| A04 | 模型调用超时或返回不完整结构 | 批次可重试，未确认候选不进入正式事项 |
| A05 | 原文有两个动作和不同期限 | 可分别审核导入，保留共同原文关系 |
| A06 | 两份协议同为第 5.2 条且标题相同 | 不因标题或条款号相同而错误合并 |
| A07 | 同一候选重复点击确认，或请求重试 | 只生成一次义务和对应首个事项 |
| A08 | 签署日与出资日不同，条款为签署后 3 个月 | 使用所关联协议的签署日和自然月规则 |
| A09 | 测试规则为不计起算日，2026-11-11 后 10 自然日 | 截止日为 2026-11-21，浏览器和服务端一致 |
| A10 | 测试规则为不计起算日且仅排周末，2026-11-06 后 5 工作日 | 预估为 2026-11-13；缺少正式确认日历时显示待确认标记 |
| A11 | 人工测试日历将某周六设为工作日、某工作日设为休息日 | 正确使用覆盖后的日历，而非固定排除周末 |
| A12 | 约定固定截止日期为 2029-12-31 | 出资日变化不改变该固定日期 |
| A13 | 事件完成后 5 工作日，但事件日期未知 | 显示待事件，没有截止日和逾期通知 |
| A14 | 交割后 30 自然日再加 5 工作日 | 两段偏移均参与，计算过程可见 |

| A16 | 2027-01-31 加 1 自然月，测试采用月末取目标月末规则 | 得到 2027-02-28；闰年及跨年用例另行覆盖 |
| A17 | 季度报送义务，定时生成器重复运行 | 每季度一个事项，完成上季度不完成下季度 |
| A18 | 持续不得迁址的义务到达区间末日 | 不自动确认整个期间均已履约，保留检查与确认流程 |

| A20 | 默认提前量下，分别剩余 30、7、1、0 天 | 分别进入 T-30、T-7、T-1、当日档位，已发送档位不抑制后续档位 |

| A22 | 两个扫描实例同时运行，或同一扫描重试 | 同一业务阶段只创建一份通知事件 |
| A23 | 服务从剩余 10 天停到剩余 1 天再恢复 | 只补当前 T-1 阶段，不连发 T-30 与 T-7 |
| A24 | 外部明确拒绝、网络超时结果未知 | 两者分开记录，遵守不同的重试及人工处理策略 |
| A25 | 已排队事项在发送前完成、取消或改期 | 旧通知跳过或按新计划重建，有处理记录 |
| A26 | 手动测试卡片或手动邮件发送 | 有手动记录，自动档位状态不改变 |
| A27 | 两个请求携带同一旧版本修改同一事项 | 一个成功，另一个收到版本冲突；不静默覆盖 |

## 15. 开发启动前需要确认的事项

| 决策 | 建议起点 | 影响 |
|---|---|---|
| 使用形态 | 先确认单人本机、单位局域网，还是持续运行的服务器 | 决定账户权限、数据库、访问方式和提醒可靠性 |
| 首版是否多人 | 若需要多人，身份与项目权限进入 P0 | 影响负责人、协作、审计和部署 |
| 日期口径 | 保留规则字段，由业务逐条或按已批准模板确认 | 决定起算、工作日、顺延、月末和复合条件算法 |
| 持续承诺和条件权利的管理范围 | 单独分类，首版至少能登记和人工检查 | 避免把权利窗口或持续义务误做普通交付任务 |
| 扫描协议占比 | 文字型文件先行，扫描件较多则 OCR 提升到 P0 | 影响文件处理工作量和审核界面 |
| 模型与数据边界 | 暂保留可替换模型适配器，生产模型另行确认 | 决定协议文本是否可发外部、费用和网络依赖 |
| 提醒对象 | 先确认统一邮箱/群，还是按项目及负责人分发 | 影响路由、权限与通知内容 |
| 逾期重复频率 | 默认首次一次，进一步策略待确认 | 决定去重键、补发和催办体验 |
| 完成审核与凭证 | 首版记录完成及可选凭证；强制要求另行确认 | 决定状态流程和审核权限 |
| 技术选型及界面风格 | 可沿用浏览器加服务，框架和视觉方案单独确定 | 不影响本文业务模型，影响实现组织 |
| 使用规模 | 确认预计项目数、事项数、文件页数、附件容量及同时在线人数 | 用于制定容量、解析耗时、备份和性能验收指标 |

在这些事项确认前，可以先完成数据模型、人工录入流程、期限引擎和模拟通知的设计验证。真实协议数据导入、真实渠道发送和生产部署应在相应配置及范围确定后进行。
